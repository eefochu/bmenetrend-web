# BMenetrend Web

This repository is the web version of BMenetrend, the Android transit app in `../bmenetrend` (locally `~/Stuff/Code/Projects/bmenetrend`). Treat the Android implementation as the product and data-contract reference. Implement web equivalents of its behaviour and use the same existing backends; do not build an unrelated app or substitute providers. Adapt interaction and layout to desktop and mobile browsers.

`AGENTS.md` is the canonical project guidance. `CLAUDE.md` must remain a relative symlink to `AGENTS.md`, so both tools read the same instructions. The Android repository has its own platform-specific guidance; do not copy its Android build/test commands into this web project.

## Client-first architecture (required)

Build this as an interactive **browser app backed by the existing Cloudflare Workers**, like the Android app is a native client of that backend. Next.js is the frontend build tool and Pages Router, not a second application backend. This project uses `output: "export"`; `bun run build` must produce a deployable static `out/` directory without requiring a Next.js server, database or auth secrets.

- Keep navigation, forms, map rendering, preferences, location, loading/error states and application state in client React components/hooks. Use browser storage for device-local preferences. Keep the small static HTML/metadata shell and browser-only dynamic imports for MapLibre and Material Web.
- Fetch remote data from the browser through typed clients in `src/lib/`, using the same public backend contracts as Android. The existing BKK Cloudflare Worker is the backend; calling it is expected and does **not** make this frontend server-heavy. Do not wrap its requests in Next API routes, tRPC, Server Actions or a duplicate proxy.
- Put secret-bearing operations, privileged upstream access, shared caching and backend validation in the existing Worker project (`../bmenetrend/tools/bkk-worker`) when a requested feature needs them. Never move BKK keys or other private credentials into browser code, localStorage or `NEXT_PUBLIC_*` configuration. Coordinate any Worker contract changes with the Android client; do not modify or deploy that separate project unless the task calls for it.
- Keep browser-side request state explicit: handle loading, empty, stale and error results; cancel superseded requests with AbortController, debounce search, bound polling to visible/active views, respect `Retry-After`, and preserve upstream timestamps. Cache according to the data's freshness needs; live vehicle data must not inherit a long-lived static asset cache.
- Do not introduce runtime SSR, React Server Components, `getServerSideProps`, Server Actions, Next API/route handlers, Prisma, NextAuth or a frontend-owned database by default. Do not fetch live or user-specific data during the static build. Add server infrastructure only for an explicit requirement that the existing Worker cannot handle.
- Stay on the Pages Router unless a migration is requested. It already supports this client-first structure; adding `'use client'` to every file does not improve it. If consulting an App Router/server-first skill, apply its guidance on typing, loading/error handling and code splitting while following **this project's client-first architecture** over its generic server-first defaults.
- Keep heavy libraries dynamically loaded; do not add blanket prefetching or large client frameworks just to call a public HTTP API. Public endpoint configuration is browser-visible. No required environment variables exist for local development; the dev launcher supplies `NEXT_PUBLIC_EMMA_GRAPHQL_URL` automatically. A static production build needs an explicitly configured, deployed adapter to make MÁV fallback work; never ship a localhost URL in production.

## Current scope

The root page is a 1:1 port of the Android UI shell, adapted for desktop: navigation (bottom bar, rail from 840px), the map screen (floating search with cookie settings button on phones (Settings sits at the bottom of the desktop navigation rail), cookie "Legközelebbi megálló" location button, draggable departures sheet that docks left on wide screens, map credits chip), search, settings, about, favourites and the planner layout. Theme mode, accent colours, light/dark street maps, Photon place search and opt-in location work. Stops, stations, live vehicles, platform departures, trip geometry/ordered stops, line variants, station/line/vehicle search, device-local favourites and Worker journey planning are now wired. The official EMMA GraphQL client supplements MÁV railway stops/vehicles and handles MÁV stop/trip fallback. No fake data is used. Offline timetable packs remain Android-only. The local ViaBusz/KanyarGO/HOMM timetables, calendars and router are ported (`src/lib/transit/planning/`, `src/lib/transit/local.ts`, assets in `public/transit/local/`). The operators' sites send no CORS headers, so the BKK Worker relays them (user decision 2026-11-24): `local-timetable-check` returns the timetable page's PDF links and the PDFs' SHA-256, and the app applies Android's review rules (reviewed fingerprints, acceptable links) before using that day's timetable; `local-live` relays the ViaBusz/KanyarGO GPS/countdown feeds, parsed in the browser (`ViabuszParser`/`KanyargoParser`), polled every 15 s only while the map shows the local area. Local stops (`local:` IDs) appear on the map from zoom 11 with boards from the verified timetable (`DepartureCalculator`) and runs from it (`local:` trip IDs); GPS vehicles have no line (the `ViabuszRouteEstimator` is not ported). When the check fails the app fails closed with Android's warnings and marks affected plans partial. Vehicle marker artwork for the three operators is rasterized from Android's vector drawables. Saved stop metadata is available locally, but saved metadata is not an offline departure prediction. Preferences for these screens (departure window, nationwide network, local planning providers) already persist in `src/lib/preferences.tsx`. The unused T3 auth/database/tRPC scaffold has been removed; the app has no local backend or sign-in requirement.

UI code: `src/components/app/` (screens, mirroring the Android `ui/` files named in each component's doc comment), `src/components/ui/` (DesignSystem.kt primitives: CookieIconButton, SegmentedItem, ConnectedSelector, ShapeIconTile, dialogs), `src/lib/theme.ts` (Theme.kt colour port), `src/lib/strings.ts` (Hungarian labels copied from Android resources), `src/styles/app.css` (component styles). Material Symbols names used by `<Icon>` must be listed in `src/pages/_document.tsx`.

UI must be a 1:1 clone of the Android app's screens (the user requested this on 2026-11-15, replacing an earlier web-only "fuller Material You" restyle). Before changing a screen, read its Compose source and compare against the running Android app (an emulator via the device tools is fine); port structure, spacing, type roles, colours and wording rather than inventing web variants. Map sheet panels follow `ViaBuszScreen.kt`: `StopPanel` (accent "Kiválasztott/Legközelebbi megálló" label, plain tinted favourite icon, 44px refresh cookie, collapse chevron, headlineSmall title, operator · mode subtitle, pill `ConnectedSelector`, `NextDepartureHero` then divider-separated `DepartureBoardRow`s, "Utolsó frissítés" footer), `RouteBrowserCard`/`DepartureDetails`/`RouteDirectionRow`, `VehiclePanel`, and `LineComponents.kt` `LineStopRow` (route-coloured rail, ringed dots, hollow ends, selected stop tinted, past stops dimmed). `NearbyPanel` shows the nearest three stations with departures as `SegmentedItem` groups (six candidate boards within 1.5 km of the user or map centre, fetched with one `arrivals-and-departures-for-stops` batch request, 60s refresh; favourites use the same batch). Tapping a departure (station board, nearby panel) opens exactly what tapping its vehicle does when that vehicle is loaded (`departure-navigation.ts`, `departureVehicle`: vehicle id, then trip or BKK trip, never the line number); otherwise the trip preview opens at once and `tripVehicle` asks `trip-details` (same parameters as the trip view, so one cache entry) for `data.entry.vehicle`, accepted only for that trip, then switches to the vehicle view. Cancelled departures never resolve; any other navigation aborts the lookup. BKK service disruptions and trip cancellations (`disruptions.ts`, `use-disruptions.ts`, `disruption-notice.tsx`, ports of `ServiceDisruptions.kt`/`DisruptionNotice.kt`) poll the Worker's `service-disruptions` once a minute while a notice is mounted and the page is visible; they match exact BKK feed identities only and appear on stop boards, line/trip/vehicle panels, favourites and journey cards/details. Station maps show BKK platform direction arrows (white on the dark map, `#334455` on the light one, as `StationSprite.kt`). A highlighted route follows `RouteLineLayer.kt` (opaque 8px casing, `#17212D` dark / white light, under a 5px stroke); its stops use the focused `StationSprite` (16dp, route-coloured single-colour dots) and arrows from BKK platform directions or, failing that, the trip shape (`stop-directions.ts`, a port of `StopDirections.collect`). A highlighted Worker-served line also loads all its live vehicles through `vehicles-for-route` (10s, independent of zoom and the 5 km map area), merged with area vehicles; the selected vehicle always stays visible. A selected vehicle's route and timeline use `vehicleLineColor` (Android's `lineColor` without a number: trains `#0066AA`, trams yellow, buses `#199DCF`). Search follows `CategorizedSearch.kt` ("Talán ezt keresed" recommendation, `StopSearchRow` with cookie mode badge, one-line uniform badges and distance pill; lines and live vehicles under Járművek); favourites follow `FavoritesScreen.kt` (name order; boards only for the favourites on screen, or the first three, at most eight; failed stations retry after 15/30/60/120 s). Destinations go through `destination.ts` (`DestinationFormatter.clean`). Nearby boards follow the map from zoom 11 (`NEARBY_MIN_ZOOM`); further out the last selection stays. Sheet hidden returns to nearby; "Útvonalnézet bezárása" leaves a route or vehicle view. Like `NativeTransitMap` `previousCamera`, the map remembers the camera when a route/trip/vehicle view opens and flies back to it when the view closes with no stop selected. A downward fling that reaches the bottom hides the sheet rather than bouncing back. Keep Android's badge artwork and dimensions. The desktop sheet and search share a responsive 460–560px width through `--docked-panel-width`; camera padding must use that same computed width, and `fitBounds` margins must not repeat it (MapLibre adds camera padding). Keep mobile sheets within the viewport, preserve keyboard focus and reduced-motion support, and retain the pinned station header/time selector.

## Transit data implementation

- `src/lib/transit/client.ts`: typed, endpoint-allowlisted production Worker client; shared in-flight requests with independent cancellation, endpoint TTLs, a bounded two-million-character/60-entry cache, 60 requests/minute and 8 plans/minute client budgets (map/nearby polling endpoints stop at 45 so taps keep headroom; a request that would free up within 8s waits instead of failing; the retry time is the oldest request + 60s, as `BkkRequestBudget`), global `Retry-After` cooldown. Station boards and trips debounce briefly so tapping through stops requests only the one left open. Map area resources use `useRemote`'s `keepPrevious`, so stop/vehicle markers (and the EMMA availability notice, which checks for missing MÁV data) do not blank out while the next area loads. MÁV area queries snap to a coarse 0.028° × 0.05° grid with a fixed 5 km box (`emma.ts` `bounds`), so small pans reuse a cached query within the local adapter's 60/minute limit. Never use `scrollIntoView` inside the map screen; it scrolls the overflow-hidden layout containers too. Do not expose keys or add a Next backend.
- `src/lib/transit/model.ts`: runtime response parsing, physical-platform identities matching `BkkWorkerParser.kt`, source timestamps, cancellations and safe polyline decoding. Vehicle timestamps are seconds; Worker envelope/planner timestamps are milliseconds. Missing/stale positions are not live observations.
- `src/lib/transit/emma.ts`: direct official MÁV GraphQL queries, bounded area rail supplementation, BKK-first identity/coupled-vehicle deduplication, direct railway boards/trips, cancellation and failure cooldown. Do not relabel this data as BKK. A successful empty primary board is not a reason to fall back, except for stops EMMA also serves (MÁV `emma:1:` and Volán): like Android's `fetchBoards` for Volán (and, on web, for rural railway stations such as Balatonföldvár too), a MÁV or Volán stop whose FUTÁR board is empty or failed, or any such window above two hours, uses the EMMA board (an empty BKK answer is kept if EMMA is down), and `emma:hkir:` trips load from EMMA (FUTÁR knows rural Volán stops such as Császár without their timetables). The local adapter accepts `1:` and `hkir:` board/trip IDs only. Browser CORS support is an external limitation. The user authorized a local development adapter on 2026-11-15; `bun run dev` starts it automatically. It forwards only the fixed queries from `emma-contract.ts` to the fixed official endpoint. See `tools/emma-relay/README.md`.
- `src/lib/transit/hooks.ts`: debounced cancellable requests; polling only for active, online, visible views. Late results cannot replace a newer selection. Explicit completed plans do not refresh on focus. Maps poll vehicles every 10s and stop metadata every 5min; boards every 20s, selected trip details every 30s. Map requests cover a bounded radius of at most 5km around a grid-snapped centre; do not imply that this is an unlimited nationwide viewport request.
- Favourites retain canonical stop IDs in existing preferences and stop metadata in `bmenetrend:stop-catalogue:v1`. Pin favourite metadata when evicting other cached stops. Do not persist live vehicle positions or pass cached predictions off as new observations.
- `src/components/app/transit-components.tsx` supplies boards, real trip/line details, source/freshness status and favourite actions. Station boards share `departure-window-selector.tsx` with nearby stops (10/20/30/60/120 minutes, browser-persisted; stored values from the older 30–300 list snap to the nearest option). `departure-card.tsx` ports Android's `NextDepartureHero` and `DepartureBoardRow`: first departure on a 20px primary-container panel, remaining rows plain on the sheet with hairline dividers, live indicators, cancellation/late states, countdown below 60 minutes and clock time thereafter. Changing the window must change the request key. `line-badge.tsx` ports `LineComponents.kt` and `TransitLineLogo.kt`; `src/lib/transit/labels.ts` ports operator, mode and service-type labels; EMMA rail badge numbers go through `railNumber` (`RailSupport.number`). Use this shared badge everywhere rather than ad hoc coloured pills.
- `public/transit/` contains resized Android PNG artwork, extracted numeric metro/HÉV panels and generated baseline station PNGs; `public/fonts/open_sans_bold.ttf` and its OFL notice are copied from Android. Provenance is documented alongside the assets. Keep the native UI badge dimensions (52×28 uniform, 76×36 metro/HÉV emblems, 28px mode icon, 17px Open Sans bold number, 5px pill corners), rail/operator colours, and orange platform indicators.
- `src/components/map/station-layout.ts` ports the current Android `StopMarkerLayout.kt`: deterministic fixed zoom-16 Mercator placement, 24px maximum offsets and reuse of existing offsets; never reposition markers from camera/viewport pixel collisions.
- `transit-layers.ts` uses GeoJSON sources and native-style raster sprites, with no station-name label layer. Station ring rasterization follows `StationSprite.kt`; vehicle PNGs and heading arrows follow `VehicleMapScene.kt` / `VehicleMarkerLayout.kt`. Rail stops show from zoom 9, other stops from 14 (`TransitMapVisibility`). Railway vehicles show from 7 in the overview layers (zoom 7–14 only); from 14 the main vehicle layers draw rail and road vehicles alike, at 0.7× (`OVERVIEW_FACTOR`, a zoom `step`, arrows too) until `VEHICLE_FULL_SIZE_ZOOM` 15. A highlighted line shows its vehicles from zoom 0 at full size and hides the overview layers. Every vehicle layer is above every station layer (route → stations → vehicles), so a bus at a stop covers it. Map taps use `map-tap.ts` (`MapTapResolver`/`StopHitTesting`): the drawn, scaled radius decides, with 10px slop and 22px minimum reach; overlapping rings below zoom 14 zoom in instead. Source stop coordinates stay unchanged; symbol offsets are visual only. Do not upload the station source on every vehicle tick.

Keep margins separate from retained overlay padding. Reframe after viewport or settled sheet-height changes; live vehicle updates must not zoom back into the selected point while a full route is shown. If an expanded mobile sheet leaves no usable map area, defer the overview until it is lowered. Preserve the pre-highlight camera restoration and theme-change camera continuity.

Dark map labels are white rather than Android's `#b9b9b9`. Regenerate them with the script instead of hand-editing. `/map/night.json` is the unchanged Android Night style, kept as reference but not currently used. Follow the app's theme mode (system by default) and preserve the camera when changing styles. Satellite view is intentionally not offered on web. Initial camera is longitude/latitude `[18.825, 47.473]`, zoom `13.2`, maximum zoom `19`.

The copied Night style originates from the Android working tree inspected on 2026-11-15 (HEAD `1f15e9c36346af3c3d8fc63311e04de03c534cf3`). Keep `public/map/licenses/` and `public/map/credits.html` alongside it; retain visible OpenFreeMap, OpenMapTiles and OpenStreetMap attribution. Resources use public URLs, with no map key required.

Use the Android app's Material You / Material 3 Expressive direction and blue fallback colours, rounded surfaces and Hungarian labels. Reuse typed Material Web wrappers from `~/components/material`. Web components and MapLibre must load only in the browser, not during SSR. Preserve keyboard navigation, accessible control names, mobile safe areas and visible attribution. ## Existing backend contracts for future features

- BKK-first Cloudflare Worker: `https://bmenetrend-bkk-proxy.bmenetrend-backend.workers.dev`, configured in Android's `app/build.gradle.kts`. Consult `tools/bkk-worker/README.md` and `data/BkkWorkerClient.kt` for endpoints and response envelopes. BKK credentials stay in Worker secrets, never in browser bundles.
- EMMA GraphQL: `https://mavplusz.hu/otp2-backend/otp/routers/default/index/graphql`, from `data/EmmaParser.kt`; queries and transport in `data/EmmaGraphqlClient.kt` and related repositories.
- Place search: Photon, `https://photon.komoot.io/api/`, from `data/PlacesRepository.kt`.
- Additional local operators retain the sources used in Android. Read their repositories when porting them.

Recheck these contracts before wiring a feature. Preserve provider-scoped identities, timestamps, source labels, bounded viewport requests, request budgets, cancellation and `Retry-After`. A successful empty result is distinct from a failed source. Browser CORS and server-origin access differ from Android: verify support before adding direct calls. Prefer the existing Cloudflare Worker for backend changes. Exception: its MÁV upstream path also fails, so this project has a user-authorized, loopback-only local MÁV adapter for development; do not replace it with Next.js route handlers or an unrestricted proxy. Android documents EMMA refusing Cloudflare-origin requests; do not claim full national coverage from the Worker alone. Photon is called directly from the browser (CORS verified); the Worker is called directly from the browser. The official EMMA endpoint currently omits `Access-Control-Allow-Origin` for localhost on both POST and preflight (checked 2026-11-15); a successful command-line request does not establish browser access. Keep its fallback errors explicit, apply retry backoff and never bypass CORS with `no-cors`, extensions or an unapproved proxy.

## Web implementation and checks

Use Bun and the committed `bun.lock`. This is a statically exported Next.js Pages Router frontend (originally scaffolded with T3), using React, TypeScript and Tailwind. There are no Next API routes, auth handlers or tRPC providers. Keep root page code in `src/pages/index.tsx`, map lifecycle in `src/components/map/`, map defaults in `src/lib/map-config.ts`, and theme tokens in `src/styles/globals.css`.

- `bun install`: install frontend dependencies. No database/client generation or secrets are required.
- `bun run dev`: prepare MapLibre's rendering worker, start the loopback MÁV adapter (prefer 8788), and start the frontend on 3000. Reuse a compatible adapter from this workspace or choose a free port if occupied, without killing existing services. The command configures the selected adapter URL automatically and stops only its owned adapter on exit.
- `bun run dev:frontend`: start only the frontend (for an explicitly configured external adapter or direct CORS testing).
- `bun run emma:relay`: run just the local adapter.
- `bun run check`: lint and TypeScript checks.
- `bun run test`: model/transport, Android marker/badge parity, map-layer style validation and hook lifecycle tests. Tests mock remote traffic; they never poll the production Worker.
- `bun run build`: prepare the MapLibre worker and export the static frontend to `out/`.
- `bun run start`: serve the built `out/` directory locally on port 3000 with a static file server.
- `bun run preview`: build and then serve the static export. Deploy `out/` to static hosting; the Cloudflare transit backend remains separate.

The **MapLibre rendering worker** in `public/maplibre/` (a browser Web Worker, separate from the Cloudflare backend) is generated from the installed MapLibre version and ignored by Git; `scripts/prepare-map-worker.mjs` runs before dev/build. Its URL includes the library version. Clean up maps, observers and event listeners on unmount. Like `NativeTransitMap`'s `onDidFailLoadingMap`, the "A térkép nem tölthető be" banner appears only when the style or its first tiles fail (initially or after a style swap); later tile/image errors are logged and retried by MapLibre, not shown as an outage. Test loading failure/retry and theme changes for map changes; report any runtime/browser verification that could not be performed. Keep secrets, database files, generated clients and build outputs out of Git. Preserve unrelated local work.

## Planner, search and MÁV failure handling

- `src/lib/transit/planning/` ports Android's planner: `core.ts` (`TripPlanner.feasible` with BKK router chains, ordering, `timelyChoices`), `alternatives.ts` (`PlannerAlternatives.select` and all its constants), `bkk-first.ts` (BKK first, 5 s; a healthy answer is returned at once, improved by a 4 s walk-averse EMMA search when every journey walks ≥10 min and by spliced connecting rides for final walks ≥8 min within plan headroom; EMMA answers when BKK fails, times out, is empty or rejected rows; vehicle+minute signatures dedupe; 30 s result reuse re-checked for feasibility; walks try a few BKK `mode=WALK` plans, then batched EMMA), `emma-planner.ts` (`TripPlanner.parse`, shared in-flight searches, `walk1`–`walk8` batches), `hybrid.ts` (`HybridTripPlanner`: all-modes and bus-only searches, 0.5/2.5/3/4 s settle windows, 10 s limit, local access/egress 1.2 km, 200 m transfers, three gateways each side), `local-network.ts`/`calendar.ts`/`local-router.ts` (bundled networks, reviewed calendars ending 2026-12-31, `LocalTimetableRouter`), `walking-store.ts` (routed walks in IndexedDB, 6-decimal keys, 60-day expiry, 4096 entries; journeys are never cached) and `session.ts` (`PlannerViewModel`: 250 ms after the form is complete, or after any change of origin, destination, departure or providers, the complete search runs in the background; Find joins it when destination, departure and providers match, the origin moved ≤20 m, it is ≤90 s old, not partial, not empty and still feasible at the new ready time; refresh and the ±15 min buttons search fresh; editing a field cancels the prefetch). The Worker `plan-trip` call uses `compact=true` like Android. Selection shows at most three cards (recommendation first). The EMMA contract and local adapter accept the bus-only plan queries and the batched walking queries.
- `planner-screen.tsx` follows `PlannerScreen.kt`: the map/form screen, then a separate results screen (back, refresh cookie, endpoints, departure chip, 15 min earlier/later, "Útvonalak" and `ItineraryCard`s), then `JourneyDetail` ("Az út lépései" timeline) from `journey-components.tsx`.
- Search recommendations use `src/lib/transit/recommendations.ts` (`StationRecommendations` scoring), not the first result. The Worker always reports its own MÁV fallback unavailable; search only notes MÁV when the app's own EMMA search failed, and shows a red error only when nothing can be listed.
- `emmaQuery`: a 4xx/GraphQL error affects only that request; timeouts, 5xx and a short `Retry-After` (adapter congestion) retry once; only an unreachable adapter (30 s) or a real 429 pauses all MÁV requests.
- Do not run `bun run build` while the user's `bun run dev` is running; it overwrites `.next` and the dev server returns 500.
